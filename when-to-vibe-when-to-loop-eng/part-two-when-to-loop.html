2 of 9 · Start with the PM

The project manager clarifies the feature before code

Start the Trinary Agents skill and discuss what “real data” must mean for this dashboard.

Agree the user outcome

The existing regional haze view reads persisted PSI and PM2.5 data through the API.

Resolve important choices

Fields, units, timestamps, region mapping, refresh behavior, and stale or missing data.

Set boundaries

Keep the existing SPA; define what historical storage and ingestion cover.

The learner talks with the PM agent first. The PM investigates the repository and skill guidance, asks focused questions, and records scope, success criteria, exclusions, risks, and unresolved decisions in the feature plan. Avoid silently deciding ingestion cadence or retention.
3 of 9 · Plan then approve

An approved plan gives the team a shared finish line

Goal

Show government PSI and PM2.5 data in the haze dashboard.

Acceptance

Data is ingested, persisted, served, and displayed with timestamps and clear failure states.

Decision

Human reviews and approves the plan before task execution starts.

Plan status: Draft → Approved → Implementing → Awaiting Human Acceptance → Accepted
The plan is not the task breakdown. The PM creates a reviewable proposal, discusses details with the human, and waits for explicit approval before decomposing and dispatching work.
4 of 9 · Decompose

The PM turns the approved plan into dependency-aware tasks

Each task has scope, dependencies, acceptance criteria, and a task README.

This is an illustrative decomposition, not a pre-approved specification. The PM inspects the codebase and skill task template, creates queued tasks, orders dependencies, and generates the feature dashboard when required. The PM owns task status changes.
5 of 9 · Run one task at a time

Every task travels through a visible handoff

PM assigns

Mark a ready task in progress and give the worker its scope.

Worker builds

Investigate, implement, verify, and write an evidence handoff.

Reviewer checks

Independently compare the change with criteria and evidence.

PM routes

Record the verdict, update status, and unblock the next task.

Task README = status and dependencies · Timestamped handoff = work evidence and recipient

Worker and reviewer do not write task status. The PM dispatches only when dependencies are done and no task is blocked. Handoffs are durable Markdown records in the project-root trinary-workspace.
6 of 9 · Review is a real gate

A change request sends the task around the loop again

Approved

PM marks the task done and reevaluates dependent tasks.

Changes requested

PM routes findings to the worker, who revises and returns evidence.

Repeat review

Reviewer checks the revision. After three unsuccessful rework rounds, ask the human.

Blocked means pause.
When an external decision blocks any task, stop dispatching until the human resolves it.
The PM reads the reviewer handoff and routes the outcome. Approved tasks become done. Changes requested move through worker rework and independent review, with up to three rounds under the skill. A blocked task pauses the whole feature workflow and requires a specific human intervention.
7 of 9 · Keep the data trustworthy

Normalize once, then persist the meaning with the value

PSI

Use the 24-hour regional PSI readings and their source timestamp.

psi_twenty_four_hourly

PM2.5

Use one-hour regional readings and preserve the source unit.

pm25_one_hourly · µg/m³

SQLite

Store region, measure, value, unit, and observation time for future use.

Missing readings stay missing. The API and UI make freshness and errors visible.

The current prompt identifies the official data.gov.sg PSI endpoint and PM2.5 endpoint. The team should confirm exact response envelopes and persistence semantics from the live contract during planning. Never present missing data as zero or invent an observation time.
8 of 9 · Connect the product

The UI should read through the API, not reach around it

Keep the mock’s useful layout. Replace fixture reads with typed API data and honest loading, empty, stale, and error states.

Integration check: selected region, measure, timestamp, and unit agree from source to screen.
The architecture follows the lesson stack: FastAPI on port 3554, the TypeScript SPA on port 3555, SQLite for persistence. Keep API credentials unnecessary for these public endpoints; confirm operational details during the plan.
9 of 9 · Finish with evidence

Done means reviewed tasks and an accepted feature

The PM completes each task cycle, then presents evidence to the human.

  • Persisted PSI and PM2.5 readings are available through FastAPI.
  • The SPA shows readings, timestamps, units, and unavailable states.
  • Worker handoffs show verification; reviewer handoffs record approval.
  • Feature checks and limitations are presented before acceptance.
